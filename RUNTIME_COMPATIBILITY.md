# Runtime compatibility

## 0.2.0 source-drop status

The supplied build scaffold is wired to the current `libxse/commonlibf4` XMake project.
It is **not** an all-runtime binary package, and no prebuilt DLL is included.

As of 2026-09-06, the upstream libxse CommonLibF4 plugin template generated by
`commonlibf4.plugin` declares:

```cpp
v.CompatibleVersions({ F4SE::RUNTIME_LATEST });
```

Therefore a DLL produced from this exact scaffold should be treated as targeting the
runtime supported as `RUNTIME_LATEST` by the dependency revision you actually build
against. Do not assume one resulting DLL will load on OG, NG and AE.

Upstream reference:
https://github.com/libxse/commonlibf4/blob/main/res/commonlibf4-plugin.cpp.in

## One-build OG / NG / AE path

`LucaDotGit/CommonLibF4` currently describes itself as an All Versions fork supporting:

- Old-Gen 1.10.163.0
- Next-Gen 1.10.984.0
- Anniversary Edition 1.11.191.0+

That fork uses a different CMake/vcpkg build setup and Address Library requirements.
UniquePlayerRedirector 0.2.0 has **not** been ported/compiled against that fork in this
source drop, so AV support is a follow-up port rather than a claim made by this package.

Upstream reference:
https://github.com/LucaDotGit/CommonLibF4

## Why the runtime logic should be portable

UniquePlayerRedirector itself intentionally contains no hardcoded executable offsets,
trampoline writes, call patches or custom relocation IDs. Its runtime work is expressed
through CommonLib/F4SE types and interfaces. That keeps the engine-specific compatibility
surface in the CommonLib build rather than duplicating address logic inside this project.
